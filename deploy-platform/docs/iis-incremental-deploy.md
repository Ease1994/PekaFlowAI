# 老 C# 项目的 IIS 增量发布

给十年前的 ASP.NET 项目用的发布方案：编译在构建机上做，发布由生产机上的**节点 Agent**
自己拉包执行。整套东西以插件和新页面的形式叠加在现有平台上，不改动原有的发布流程。

支持范围：**Windows Server 2012 R2 / IIS 8.5 及以上**。更老的 2003/2008 不在支持范围内
（跑不了现代 JRE，也没有可靠的 TLS 支持）。

## 整体流程

```
开发提单（发布提交页）
      │  项目 / 流水线 / 代码版本 / 发布清单 / 更新日志
      ▼
发布人员核对 → 点「发布」
      │  清单作为执行参数交给流水线
      ▼
构建机 Job：git-checkout → MSBuild 编译 → 提取增量发布包（上传到平台）
      ▼
节点 Job（派发到生产机的节点 Agent）：
      IIS 停应用池 → 发送文件到节点（自动备份+解压） → IIS 启应用池
```

关键点：**平台从不往生产机推东西**，包是节点 Agent 自己拉的，生产机不用开任何入站端口。

## 一、在生产机上装节点 Agent

不用往服务器上传任何文件——脚本和 jar 都从平台下载。在节点服务器上**以管理员身份**
打开 PowerShell，粘贴节点管理页给出的两行命令：

```powershell
iwr http://平台地址:8080/api/v1/agents/install-script?role=node -OutFile install-node.ps1
.\install-node.ps1 -Name iis-prod-01 -AllowPaths D:\wwwroot\o2o -AllowIis DefaultAppPool,site:www -EnrollToken <接入凭证>
```

脚本会停掉旧进程、下载 jar、生成启动器并拉起。升级时重跑同样的命令即可。

平台地址在下载脚本时就烤进去了，不用再传 `-Server`。接入凭证在节点管理页复制，
用于下载 jar 和首次注册；注册后凭据落在 `%USERPROFILE%\.release-agent\enrolled\`，
Agent 之后靠它自己续期。**装节点不需要平台管理员密码**——生产服务器上不该出现它。

前置条件：

- **JRE 8+**
- **必须以管理员身份运行**：启停 IIS 应用池需要管理员权限，脚本会先检查，不满足直接退出
- `-AllowPaths` 是这台机器的安全边界：节点只会在这些目录里写文件，其它路径一律拒绝。
  多个目录用逗号分隔。**只填站点根目录**——脚本会拒绝盘符根目录，也会校验目录是否真的存在。

装完后机器重启需要手动拉起 `%USERPROFILE%\rp-node\start-node.cmd`（同样要管理员身份）。
想开机自启，用 nssm 之类的工具把它注册成 Windows 服务（服务默认以 SYSTEM 运行，权限足够）。

不想用脚本的话，节点管理页的安装弹窗切到「手动命令」能拿到等价的 java 命令。
构建机同理，构建机页面也有一键安装命令（`role=builder` / `role=builder-linux`）。

节点和构建机的区别：

| | 构建机 | 节点 |
|---|---|---|
| 干什么 | 拉代码、编译、打包 | 只发文件和启停 IIS |
| 能跑脚本吗 | 能 | **不能** |
| 会下载插件吗 | 会 | **不会**，两个发布动作是内置的 |
| 写盘范围 | 工作空间 | 只有 `--allow-paths` 声明的目录 |
| 怎么接任务 | 按标签抢 | 只做被指名派给自己的任务 |

节点永远不会领到构建任务——构建任务体里带着仓库凭证，不该出现在生产机上。

## 二、搭发布流水线

一条流水线两个 Job：

### Job 1：构建（跑在 Windows 构建机上）

需要构建机装有 Visual Studio Build Tools 和 Python 3。

1. **代码拉取**（git-checkout）
2. **MSBuild 编译**（msbuild-build）
   - 项目文件：`src/MyApp.Web/MyApp.Web.csproj`
   - 编译方式：**Web 项目**（走 `_CopyWebApplication`，产出的目录结构和生产站点根目录一一对应）
   - 输出目录：`_publish`
3. **提取增量发布包**（pack-incremental）
   - 编译产物目录：`_publish`
   - 发布清单：填 `${{DEPLOY_MANIFEST}}`，值来自发布提交单

### Job 2：发布（步骤里选节点，会自动派到那台机器）

1. **IIS 启停控制**（iis-control）：目标节点 = iis-prod-01，操作 = 停止，对象 = 应用池，名称 = 你的应用池名
2. **发送文件到节点**（file-transfer）：目标节点 = iis-prod-01，站点根目录 = `D:\wwwroot\o2o`
3. **IIS 启停控制**：同 1，操作改成**启动**

节点是在插件参数里选的，不用配 Job 的构建机标签。连续发往同一节点的步骤会合并成一段派给它，
所以「停 → 发 → 启」是在同一台机器上顺序执行的。

## 三、发布清单怎么写

一行一条，相对**编译产物根目录**（也就是生产站点根目录）：

```
bin/*.dll          # 通配符
Areas/             # 目录，以 / 结尾表示整个递归
Views/
Content/o2o-theme.css   # 单个文件
!bin/*.pdb         # ! 开头是排除
# 井号开头是注释
```

不允许绝对路径和 `..`。清单只在提交单里写一次，打包、备份、覆盖三处用的都是它，
不会出现「备份的和发的不是同一批文件」。

## 四、备份和回滚

「发送文件到节点」在解压前会自动备份，按项目和流水线分层，每次发布一个独立子目录：

```
D:\release-backup\电商项目\o2o-生产发布\20260819-143022\
    bin\App.dll              ← 本次会被覆盖的文件的原件
    _backup_files.txt        ← 被覆盖的文件清单
    _added_files.txt         ← 本次新增的文件清单（回滚时要删掉它们）
```

备份根是安装节点时定的（Windows 默认站点盘 `X:\release-backup`，Linux 默认安装目录第一层下的 `release-backup`）。流水线步骤默认不用填；只有要在这个根下面再分一层时才打开「自定义备份目录」。换磁盘去节点管理安装命令里填备份根，不要在步骤里填另一块盘的绝对路径。
分层是为了在生产机上直接翻目录就能找到某条线的历史版本，不用回平台查任务号；
目录名带时分秒而不只是日期，是因为同一天往往要发好几次，只按日期后一次会盖掉前一次。

两个地方不能填：**C 盘等系统目录**，备份会把盘写满，盘一满 IIS 连日志都写不出来；
**站点目录内部**，备份含 DLL 和 web.config，放进站点会被 IIS 当静态文件下载，
等于把数据库连接串挂到公网上。节点会直接拒绝这两类路径并说明原因。

新增文件之所以单独记，是因为增量回滚不只是把旧文件换回去，还得把这次新加的删干净，
否则会留下一堆残留——老代码一旦按名字加载到新版本才有的 DLL，故障现象会比回滚前更难查。
默认按流水线保留最近 20 份，超出自动清理最旧的。

### 一键回滚

在发布记录上点「回滚」，撤销的就是那一次发布：把备份的文件盖回去、删掉那次新增的文件，
前后按发布时的配置停起应用池。**不重新拉代码、不重新编译**，通常几秒完成。

之所以不走「用老代码重新构建再发一遍」：老代码未必还构建得出来（NuGet 源、SDK 版本、
依赖包都在变），而故障现场最缺的就是时间。

发布成功时节点会把「备份目录在哪、发布时怎么停起的应用池」上报给平台，存成部署记录，
回滚就是照着它反向执行一次。所以有三种情况回滚不了，平台会在确认框里直接说明：

- **发布发生在平台支持回滚之前**，或节点 Agent 版本太旧没有上报能力 → 升级节点后的发布才可回滚
- **已经撤销过一次** → 备份已经盖回生产了，再撤一次只会把更早的版本翻上来
- **备份目录被清理了**（超过保留份数）→ 节点会直接报错并说明，不会half-way改坏站点

还有一种情况平台会警告但允许继续：**这个站点在这次之后又发布过**。这时撤销会把之后
那次的内容一并回退，确认框里会写清楚是被哪次发布覆盖的。

回滚跑完，被撤销的那条发布记录会标成「已回滚」，避免它在历史里一直挂着绿色的「成功」，
让后来排查的人以为线上还是这个版本。

## 五、第一次上线前先预演

两个插件都有 `dryRun` 开关，强烈建议第一次先各跑一遍：

- **提取增量发布包** 的预演：只列出清单命中了哪些文件，确认范围对不对
- **发送文件到节点** 的预演：只打印「会覆盖哪些、会新增哪些」，不动生产文件

预演能提前发现两类典型问题：清单写漏了（比如忘了 Web.config），或者清单写太宽
（比如 `bin/` 把整个依赖目录都带上了）。

## 六、常见问题

**「节点不支持步骤 xxx」**
把编译类步骤放到了节点的 Job 里。节点只执行「发送文件到节点」「还原备份」和
「IIS 启停控制」，其它步骤要放在构建机的 Job 里。

**「目标目录 xxx 不在本节点允许的范围内」**
插件里填的站点目录不在节点启动参数的 `--allow-paths` 内。确认路径没写错；
确实要发到那里的话，改节点启动参数后重启节点。

**「appcmd 执行失败：拒绝访问」**
节点 Agent 没以管理员身份运行。停掉后用管理员 cmd 重新启动。

**「拉取增量包失败」**
本次发布没跑「提取增量发布包」步骤，或者那一步失败了。去执行详情里看构建 Job 的日志。

**应用池停了但 dll 还是被占用**
IIS 停应用池后工作进程退出需要一点时间，`iis-control` 会等到状态真的变成 Stopped 才继续。
如果还是占用，检查是不是有别的站点也在用同一个目录。
