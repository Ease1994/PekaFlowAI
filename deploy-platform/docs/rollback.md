# 一键回滚

平台的回滚是**撤销上一次部署**，不是「用老代码重新发一遍」。

之所以这样设计：老代码未必还构建得出来——NuGet 源、SDK 版本、基础镜像、依赖包
都在随时间变化，等到线上出故障才发现构建不过，就彻底没退路了。而且完整走一遍
构建流程要几分钟，故障现场最缺的就是这几分钟。

撤销所需的东西，上次部署的时候就已经在目标环境留下了：增量发布留了备份文件，
容器发布留了上一个镜像 tag，K8s 自己就记着 revision。回滚只是把它们用回去。

## 部署记录

每个部署步骤成功后，会往平台登记一条**部署记录**，写清楚「怎么撤销我」：

| 部署类型 | 记什么 | 撤销动作 |
|---|---|---|
| 增量文件发布 | 备份目录、站点目录、发布时的 IIS 启停配置 | 还原备份文件 + 删除新增文件 |
| 容器镜像发布 | 部署前容器跑的镜像、容器配置 | 用上一个镜像重建容器 |
| K8s 发布 | 部署前的 revision | `kubectl rollout undo --to-revision=N` |

记录里带着执行部署的那台机器。回滚必须回到同一台：备份文件只在那台节点的磁盘上，
kubeconfig 和 docker 上下文也只在那台构建机上，派到别处必然扑空。

一条记录只能撤销一次。撤销后备份已经盖回生产了，再撤一遍只会把更早的版本翻上来。

## 用起来是什么样

在发布记录上点「回滚」，确认框会先列出**即将执行的每一步**（停哪个池、停哪个站、
还原哪个目录、再起哪些），以及撤销哪个站点、还原多少文件、或者回退到哪个
revision。确认后生成一条新的发布记录，只跑撤销动作，不碰构建机。

一次发布打了多台节点时，回滚也按滚动进行：**后发的先撤**，一台整段（停 → 还原 → 起）
成功后再动下一台，和发布时「一个 Job 里按节点抄三遍」同一条链路，始终只停一台。

同一份备份不能同时开两张回滚单：待审批、排队、执行中都算在飞，再点会被拒绝。
回滚单真正开跑前还会再核对一次部署记录——已经撤过或记录不完整的，不会再动手。

需要审批的分组，回滚同样要过审，也可以走应急跳审（会留审计并通知审批人）。

回滚跑完，被撤销的那条记录会标成「已回滚」，不再挂着绿色的「成功」误导后来的人。

## 什么情况下回滚不了

确认框会直接说明原因，不用去日志里翻：

- **没有部署记录**：这次发布没真正往目标环境写东西，或者发生在平台支持回滚之前
  （节点 Agent 版本太旧也算）。只能用上一个正常版本重新发一次
- **已经撤销过**：同上，备份已经用掉了
- **备份目录被清理**：增量发布默认保留最近 20 份备份，太老的会被清掉。
  节点会在动手前发现并中止，不会把站点改成一半新一半旧
- **K8s revision 被清理**：受 `revisionHistoryLimit` 限制，太老的 revision 不在了

还有一种情况允许继续但会警告：**这个节点上的这个目录，在这次之后又被更新的构建覆盖过**。
回滚是把这次留下的备份盖回去，目录上现在如果已经是更晚那次写的，盖回去等于把更晚那次也撤掉。
确认框会写出节点名字、IP（节点页上的「IP / 主机」）和覆盖它的**构建号**（执行历史上看到的那个 #N），不是全库发布主键，也不是节点表 id。
判断按「节点 + 目录」：负载均衡后面三台机器写同一个站点路径，不会互相当成覆盖。

## 各类型的注意事项

### 增量文件发布

回滚在节点上执行，顺序按**当时那次发布整段重放**：停应用池 / 停站点 → 还原文件
→ 起应用池 / 起站点。启停拆在不同 Job 里、中间夹了构建步骤，也会按同一次发布
拼起来回放，不能只看传文件旁边最近一条。一次发布里传了两个站点，各自套自己
那一套 IIS，不会串台。

发布时用 recycle 回收应用池的，回滚同样回收。停起的参数直接沿用发布时那一步：
发布时需要停池才能换 DLL，还原同样在换 DLL；发布时没停，回滚也不会自作主张去停。

备份目录、站点目录缺任何一个，整次发布都不能一键回滚，避免只还原其中几个站点
把环境拆成一半新一半旧。回滚跑成功后由平台销账；节点上报失败也不会让同一份
备份再被撤一次。

动手前会先校验备份完整性，缺文件就中止，避免站点停在新旧混合状态。删不掉的文件
（多半是应用池没停干净、被 w3wp 占着）会判失败，不会悄悄放过——留着新版本才有的
DLL，老代码一旦按名字加载到它，故障现象会比回滚前更难查。

### 容器镜像发布

镜像 tag 别用 `latest`。回滚靠的是「上一个版本的镜像还在仓库里」，所有版本都叫
latest 的话，回退到哪一个都无从谈起。`docker-build` 插件默认用构建号当 tag。

首次部署（目标上原本没有同名容器）没有回滚点，插件会明确告警。

### K8s 发布

同样别用固定 tag：K8s 认 tag 不认内容，同名 tag 换了内容不会触发滚动更新。

Pod 里有 sidecar 时必须填容器名，否则 `set image` 会把 sidecar 也换成业务镜像。

kubeconfig 以插件参数传入，跑的时候落成临时文件（权限 600），任务结束立即删除。
