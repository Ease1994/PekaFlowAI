# PekaFlowAI · Deployment

[中文](部署文档.md) · [English](部署文档.en.md)

This guide is for people installing [PekaFlowAI](https://github.com/Ease1994/PekaFlowAI) on their own machine or in a data center. It follows the real `docker-compose.yml`, environment variables, and agent install scripts in this repo. It does not invent a fake stack.

After reading you should be able to: open the UI locally → bring the full stack up with Compose → configure models and logs → install build agents and deploy nodes → serve over HTTPS → back up, upgrade, and change the public URL.

Product usage: [feature spec](功能说明书.md) (Chinese). Modules and pitfalls: [developer handbook](../../docs/开发者手册.md) (Chinese). Agent flags: [agent-java/README.md](../backend/agent-java/README.md).

## 1. What you are installing

The product has three layers. Missing one means you can look at the UI but cannot release:

| Layer | Where it runs | What it does |
|-------|----------------|--------------|
| Interaction and orchestration | Frontend + backend in this repo | Web UI, AI assistant, pipelines, approvals, RBAC |
| Data | MySQL, Redis, Elasticsearch (bundled in Compose) | Business data, cron, live logs; build / AI logs archived per day |
| Execution | `deploy-agent.jar` on each machine | Builders compile and pack; nodes write sites and start/stop services |

Builders and nodes **pull** work. The platform does not need inbound ports to them. Those machines must be able to reach the platform (IP or hostname).

Compose also starts a **harness-runner**: it runs third-party agent tools only, read-only, unprivileged, on the internal Compose network. If it is down, those tools are refused. They never fall back to running inside the backend process.

## 2. Three ways to install

| | A Local development | B Compose trial | C Production |
|--|---------------------|-----------------|--------------|
| Who | Changing code, looking at the UI | Full trial, small team first run | Serving internally or on the public internet |
| Database | SQLite file | MySQL 8 in Compose | Same Compose, or your own MySQL |
| Redis | Optional (cron will not fire) | Password required in Compose | Password required; do not publish to the host |
| Elasticsearch | localhost:9200 or skip | Bundled single node | Use the bundled node, or point Settings at your own cluster |
| Frontend | http://localhost:5173 | http://localhost:8000 | `https://your-domain` behind a reverse proxy |
| Admin password | Demo `admin` / `admin123` | Demo is allowed; change it immediately | Must set `BOOTSTRAP_ADMIN_PASSWORD` |
| Agent | You can enroll this machine as a builder | Follow sections 7 and 8 | One-shot script on every target |

Do not take A's demo password and SQLite into production.

## 3. Machines, dependencies, ports

### 3.1 Platform host (Compose or local frontend/backend)

| Item | Requirement |
|------|-------------|
| CPU / RAM | Trial: 2 cores / 4 GB is enough (ES heap defaults to 512 MB). Production: 4 cores / 8 GB and up |
| Disk | OS disk plus a **data disk**. Artifacts live in `backend-data`; logs live in `es-data`; both grow |
| Software (A) | Python 3.10+ (3.11/3.12 recommended), Node.js 18+, Git. On Windows use `py`, not `python3` (often the Store redirector) |
| Software (B/C) | Docker Engine + Docker Compose v2 |
| Compile the agent | After changing `agent-java/src` you need JDK 8 `javac` (see section 14) |

### 3.2 Builders / deploy nodes

| Role | OS | Must have |
|------|----|-----------|
| Builder | Windows / Linux / macOS | JRE/JDK 8+; disk for workspace (clone, compile output) |
| Windows node | Windows Server 2012 R2+ | **Administrator** PowerShell; JRE 8+; only site directories on the allow-list |
| Linux node | Linux with systemd | Run the install script as **root**; can download JDK 8 from the platform (section 9) |

Nodes **do not compile, clone, or run arbitrary scripts**. Use a builder for compile work.

### 3.3 Ports (platform host)

| Port | Service | Published on the host by default |
|------|---------|----------------------------------|
| 8000 | Frontend Nginx (80 inside the container) | Yes. Browsers go here |
| 8080 | Backend API | Yes. Agents also connect here. Behind a reverse proxy you can expose only 443 |
| 8090 | harness-runner | **No**. Compose internal network only |
| 3306 | MySQL | **No** in production. Overlay `docker-compose.debug.yml` only when debugging |
| 6379 | Redis | **No** in production. Same as MySQL |
| 9200 | Elasticsearch | **No** in production. Same as MySQL |

Firewall: allow browsers and agents to reach 8000 (or 443) and the backend address they actually use. Do not expose 3306, 6379, 8090, or 9200 to the public internet.

## 4. A. Local development (SQLite)

For changing code. No Docker. Steps are the same on Windows, Linux, and macOS; only the venv activate command differs.

Application code lives under `deploy-platform/` inside the repo.

### 4.1 Backend

```bash
git clone https://github.com/Ease1994/PekaFlowAI.git
cd PekaFlowAI/deploy-platform/backend

# Windows
py -m venv .venv
.venv\Scripts\activate

# Linux / macOS
python3 -m venv .venv
source .venv/bin/activate

pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8080
```

`--host 0.0.0.0` is required, otherwise VMs / LAN clients cannot connect. First boot will:

- Create the SQLite file `deploy-platform/backend/deploy_platform.db`
- Write `deploy-platform/backend/data/.secrets.json` (JWT / AES / runner token; **do not commit**)
- Create admin `admin` / `admin123` and log a warning that this is a demo password

Optional: copy `backend/.env.example` to `backend/.env`. Without `DATABASE_URL` it stays on SQLite. Browse the in-app API handbook after login; you do not need `/docs`.

Repo start scripts (run from `deploy-platform/`):

```bash
# Git Bash / Linux
bash scripts/start-backend.sh

# Windows CMD
scripts\start-backend.bat
```

### 4.2 Frontend

Another terminal:

```bash
cd PekaFlowAI/deploy-platform/frontend
npm install
npm run dev -- --host 0.0.0.0
```

Open http://localhost:5173 . Vite proxies `/api` to `http://localhost:8080`, so the dev machine does not need CORS.

Sign in as `admin` / `admin123`. Then do section 6, or the assistant cannot talk.

### 4.3 Switch to local MySQL (still development)

Copy `backend/.env.example` to `.env` and set `DATABASE_URL`, for example:

```
DATABASE_URL=mysql+pymysql://root:your-password@127.0.0.1:3306/deploy_platform?charset=utf8mb4
```

Create empty database `deploy_platform` with utf8mb4 first. Restart the backend.

## 5. B. Full Docker Compose stack

Recommended for “get a complete run” and most self-hosted installs. The compose file is **`deploy-platform/docker-compose.yml`**, not the repo root.

It starts: MySQL 8, Redis 7, Elasticsearch 8, secrets-init, backend, harness-runner, frontend.

### 5.1 One-command start

From the repo root:

```bash
bash deploy/pekaflow.sh install
```

If `.env` is missing the script copies `.env.example` and runs `docker compose up -d --build`. An existing `.env` is never overwritten.

You can also prepare the file yourself:

```bash
cd PekaFlowAI/deploy-platform
cp .env.example .env
```

On Windows, copy the file by hand. `.env` must sit next to `docker-compose.yml`. **Never commit a filled `.env`.**

`.env.example` already has trial passwords (MySQL `rp-mysql`, Redis `rp-redis`, admin `admin` / `admin123`). After copying:

```bash
docker compose up -d --build
```

For production, change every secret in `.env` first. The password in `DATABASE_URL` must match `MYSQL_ROOT_PASSWORD` **exactly**. Changing MySQL / Redis passwords on an existing volume has no effect; use `docker compose down -v` and start over (this wipes the database). **Do not rotate JWT / AES on a running install**, or Git credentials will not decrypt. Take `.env` with you when migrating hosts.

Optional:

```bash
# Browser CORS allow-list, comma-separated. Under Compose the frontend Nginx proxies /api same-origin, so this is usually empty
CORS_ORIGINS=
```

### 5.2 Check readiness

The first run pulls images and builds frontend and backend; it can take several minutes:

```bash
docker compose ps
docker compose logs -f backend
```

Open the browser after backend logs show tables / admin ready and `docker compose ps` shows backend and frontend as healthy (or at least running).

Entries:

- Frontend: http://localhost:8000
- API: http://localhost:8080 (`/docs` is **off** by default)
- Health: `GET http://localhost:8080/api/v1/health` should return `status: up`

### 5.3 Publish database ports only when debugging

Do not use this in production. When a local client must reach MySQL / Redis:

```bash
docker compose -f docker-compose.yml -f docker-compose.debug.yml up -d
```

Then 3306, 6379 and 9200 appear on the host. Tear down the debug overlay when you are done.

### 5.4 Where data lives

Four Docker volumes:

| Volume | Contents |
|--------|----------|
| `mysql-data` | MySQL files |
| `redis-data` | Redis AOF |
| `es-data` | Build / AI audit indexes (`rp-exec-logs-YYYY-MM-DD`, `rp-assist-logs-YYYY-MM-DD`) |
| `backend-data` | `data/.secrets.json`, artifacts, uploaded plugins, skill packs, header images, Linux JDK tarball (`shared-packs/jdk-linux/`), chat uploads |

Recreating containers **does not** wipe volumes. `docker compose down -v` **does**, which empties this install.

## 6. What you must do after first login

Applies to both A and B. After the admin signs in, do this in order. Skip a step and later you get “assistant is silent / scripts have the wrong URL / logs are empty”.

### 6.1 Change the admin password immediately

The demo password is for a local machine only. Production should already have `BOOTSTRAP_ADMIN_PASSWORD` in `.env`. If it is still `admin123`, open Users and change it.

### 6.2 Configure a model (otherwise AI Agent cannot talk)

Open **Models** (`/models`). Add an **OpenAI-compatible** provider:

- API Base, for example `https://api.deepseek.com/v1` or your gateway `/v1`
- API Key
- Then a model name that matches the provider console, and mark it available

In **AI Agent** (`/ai`) send “who are you”. Streaming text means it works.

### 6.3 Set the public URL `public_app_base`

Open **Settings** (`/settings`, admin only).

**Site root URL** is the address users actually open in the browser, with no trailing slash:

- Local Compose: `http://localhost:8000`
- LAN: `http://192.0.2.10:8000` (use the platform host’s real IP)
- Domain: `https://deploy.example.com`

Install scripts, password-reset mail, and some redirects all use this value. If empty, the platform uses the `Host` of **that request**, which is easy to get wrong when you have more than one entry.

### 6.4 Redis (already injected under Compose)

Compose passes `REDIS_HOST=redis` and `REDIS_PASSWORD` to the backend. Pipeline cron uses a Redis delayed queue. Local development without Redis can leave the settings empty or localhost: cron will not run; everything else still works.

### 6.5 Elasticsearch (bundled in Compose)

Build logs are **Redis live + ES daily archive**. They cannot fall back to MySQL. Compose starts a single-node ES at `http://elasticsearch:9200` (no auth) and writes that URL into Settings on first boot.

- Build logs: `rp-exec-logs-YYYY-MM-DD` (Asia/Shanghai calendar day; prefix is editable in Settings)
- AI audit: `rp-assist-logs-YYYY-MM-DD` (fixed prefix, not the Settings field)

To use your own cluster: open **Settings**, change the ES URL / credentials / index prefix, and save. No backend restart. The env var does not lock the saved value.

Local development (A) without Compose talks to `http://localhost:9200`. You can run the same single-node image, or skip it (history empty, health shows ES down; releases still run).

If ES will not start on Linux, `vm.max_map_count` is often too low: `sysctl -w vm.max_map_count=262144`.

### 6.6 Keep emergency skip-approval off

“Emergency skip approval” in Settings is off by default. Do not turn it on on a new install unless you understand group-level skip.

### 6.7 Other items as needed

LDAP, WeCom, SMTP, TOTP, display name, header image, session days: all on the same page. Save is enough; no backend restart. Meanings are in section 15.

Only these require a restart (or `docker compose up -d` after editing Compose `.env`):

`DATABASE_URL`, `JWT_SECRET`, `AES_KEY`, `BOOTSTRAP_ADMIN_PASSWORD`, `CORS_ORIGINS`, `API_DOCS_ENABLED`

## 7. Install a build agent

Builders check out git, compile, and pack. On **Agents** (`/agents`) → **Add builder**, copy the enroll token and the install command. The command already includes the current platform URL.

**First registration on a new machine must include the enroll token.** After that, credentials live on the machine:

- Linux / macOS: `~/.release-agent/enrolled/`
- Windows builder scripts also write a launcher under `C:\ProgramData\release-agent\builder\`

Later restarts and jar upgrades do not need the token again. If it leaks, click “Rotate enroll token” on the page; **machines already enrolled are not affected**.

### 7.1 Windows builder

The machine needs a **working** JRE/JDK 8+ (a leftover `javapath` junction on PATH after uninstall is not enough). In a normal or Administrator PowerShell:

```powershell
iwr http://platform-host:8080/api/v1/agents/install-script?role=builder -OutFile install-agent.ps1
.\install-agent.ps1 -EnrollToken <token-from-the-page>
```

If you downloaded the script from the page, the URL is already filled. Optional:

| Flag | Meaning | Default |
|------|---------|---------|
| `-Server` | Platform root URL including scheme | Filled in the script |
| `-Name` | Machine name, unique on the platform | Computer name |
| `-Tags` | Scheduling tags, comma or array | OS tags |
| `-Env` | `prod` / `test` / `uat` / `staging` / `dev` or a custom lowercase code | `prod` |
| `-Workspace` | Clone and artifact directory; **disk-heavy** | `workspace` under the install dir |
| `-Concurrency` | Parallel tasks, 1–32 | 8 |
| `-WorkDir` | Install directory | `%USERPROFILE%\release-agent` |

If C: is tight: `-Workspace D:\rp-workspace`.

Install creates scheduled task **RELEASE-Build-Agent**: starts at boot, recovers within about two minutes if the process dies. After the platform publishes a new jar, the builder upgrades itself when **idle**.

`Env` applies only the **first** time the platform sees this machine. Later the page wins, so a reinstall does not wipe a human-edited environment.

### 7.2 Linux / macOS builder

```bash
curl -fsSL "http://platform-host:8080/api/v1/agents/install-script?role=builder-linux" -o install-agent.sh
ENROLL_TOKEN=<token-from-the-page> bash install-agent.sh
```

Common env vars: `SERVER`, `NAME`, `TAGS`, `ENV`, `WORK_DIR`, `WORKSPACE`, `CONCURRENCY`. Tight system disk: `WORKSPACE=/data/release-workspace`.

The script checks the downloaded jar against the platform `jar-sha256` and deletes/retries on mismatch.

### 7.3 Manual start (debug)

```bash
java -jar deploy-agent.jar --server http://192.0.2.10:8080 --name linux-build-01 \
  --tags linux,maven,docker --enroll-token <token>
```

The token can also be `RELEASE_ENROLL_TOKEN`, so it does not land in shell history. Home directory can be `RELEASE_AGENT_HOME`; default is `~/.release-agent`.

Workspace is isolated per pipeline: under `--workspace` / `WORKSPACE` you get `p-{pipeline-id}/src/`.

After install, **Agents** should show online. If not, see section 16.

## 8. Install a deploy node

A node does three things: write files into allow-listed directories, restore backups, and start/stop services you allowed. The allow-list is the safety boundary: **empty paths, a drive root, and `/` are never “everything”.**

Copy the enroll token from **Nodes** (`/nodes`) → **Add node**.

### 8.1 Windows node (IIS)

Open PowerShell **as Administrator** (app-pool control needs it):

```powershell
iwr http://platform-host:8080/api/v1/agents/install-script?role=node -OutFile install-node.ps1
.\install-node.ps1 -AllowPaths D:\wwwroot\mysite -EnrollToken <token>
```

| Flag | Meaning |
|------|---------|
| `-AllowPaths` | **Required**. Site roots that may be written, comma-separated. Site directories only, not `D:\` |
| `-AllowIis` | Optional. Further restrict by app-pool / site name; if omitted, physical path must fall under AllowPaths |
| `-Env` | Default `prod`. `test`/`dev` file push skips approval; others require it. First enrollment only |
| `-BackupRoot` | Backup root. Must be **outside** the site. Empty uses `X:\release-backup` on the site’s drive |
| `-WorkDir` | Install directory, default `rp-node` under the user profile |

Backups include DLLs and `web.config`. Putting them inside the site would serve connection strings as static files. Install creates scheduled task **RELEASE-Node-Agent**.

Add more allow paths later on the Nodes page; they go out on heartbeat, no reinstall. Jar upgrades: **do not** invent a local process. Click “Upgrade” on the platform and wait until the current release finishes.

### 8.2 Linux node (systemd)

As **root** on the node:

```bash
curl -fsSL "http://platform-host:8080/api/v1/agents/install-script?role=node-linux" -o install-node.sh
ALLOW_PATHS=/var/www/mysite ALLOW_SERVICES=systemd:nginx ENROLL_TOKEN=<token> bash install-node.sh
```

| Variable | Meaning |
|----------|---------|
| `ALLOW_PATHS` | **Required**. Directories that may be written, comma-separated. Do not use `/` |
| `ALLOW_SERVICES` | Services the agent may control, e.g. `systemd:nginx,docker:web`. A name without a type is systemd. Leave empty if you only copy files |
| `RUN_USER` | Account the agent runs as, default `release` (created, no login). Can be `www-data` |
| `INSTALL_DIR` | Directory you are in when installing. Page commands often set `INSTALL_DIR=$(pwd)`. Backup root is taken from the first path segment: `/data/soft/release` → `/data/release-backup` |
| `BACKUP_ROOT` | Explicit backup root; otherwise derived as above and chowned to the run user |
| `ENV` | Same as Windows, default `prod` |
| `WORK_DIR` | Default `/opt/release-node` |

The agent **does not run as root**. Services it may stop go through a sudoers allow-list generated by this script (`/etc/sudoers.d/release-node`). Changing start flags cannot bypass it.

If the machine has no usable Java 8+, the script downloads JDK 8 from the platform with the enroll token and continues only after `java -version` succeeds. A bad Java never gets the service installed. Upload the tarball on the platform first (section 9).

The systemd unit defaults to `rp-node`. After changing the platform URL, re-run the install script (section 12). Do not edit a single env var by hand.

## 9. Linux node JDK package

Windows nodes still need a local JRE. Linux nodes can pull one from the install script.

Upload an official or Adoptium **x64 Linux JDK 8** tar.gz (for example `jdk-8u271-linux-x64.tar.gz`) once on **Nodes**. It is stored on the data volume at `data/shared-packs/jdk-linux/`. Rebuilding the image does not delete it.

For local development you can also drop it in `deploy-platform/backend/agent-java/jdk-linux/`; first boot copies it onto the volume.

Without this file the platform still starts. Node install 404s at the JDK download step. The API is `GET /api/v1/agents/jdk-linux` (enroll token required).

## 10. Verify the platform is alive

```bash
# Health (no login)
curl http://localhost:8080/api/v1/health

# Sign in
curl -X POST http://localhost:8080/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"your-admin-password"}'

# Use the returned token
curl http://localhost:8080/api/v1/projects \
  -H "Authorization: Bearer <token>"
```

Also check by hand:

1. Models is configured and AI Agent streams a reply.
2. Agents shows at least one online builder.
3. Nodes shows at least one online node, allow paths matching the real site.
4. Create a test pipeline, ask the assistant to release it, and confirm the pipeline id on the card is the one you meant.
5. An incremental-pack step with an empty manifest must **refuse to run**, never silently pack everything. That is the production-safety default, not a bug.

The API catalog is the in-app **API handbook** (official Swagger UI, `GET /api/v1/meta/openapi`, login required). FastAPI `/docs` stays off by default; **do not** reverse-proxy it to the public internet.

## 11. Production hardening and HTTPS

### 11.1 Checklist

- Trial passwords in `.env` are for a local machine only. Change them to your own long random values before serving anything.
- Do not use `docker-compose.debug.yml` to publish 3306/6379/9200 on a public NIC.
- Keep `API_DOCS_ENABLED` off.
- Settings `public_app_base` is `https://your-domain`.
- Change the admin password; turn on TOTP if you want.
- Keep emergency skip-approval off.
- Compose already runs ES; point Settings at your own cluster if you have one.
- Backend is **one worker** (the image already is). Cron is an in-process thread; extra workers would fire twice. Multiple instances must share the same `JWT_SECRET` / `AES_KEY` and the same database, and must not run more than one scheduler.

### 11.2 Outer Nginx / load balancer (TLS offload)

Browsers hit 443 only. Proxy to Compose **8000** (frontend Nginx then proxies `/api` to the backend). Agents can use the same hostname `/api` or talk to 8080 directly; pick one and write it into `public_app_base` and the install scripts. Do not mix.

The outer proxy must forward:

```nginx
server {
    listen 443 ssl;
    server_name deploy.example.com;
    # ssl_certificate / ssl_certificate_key — your certs

    client_max_body_size 400m;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering off;
        proxy_read_timeout 300s;
    }
}
```

If you omit `X-Forwarded-Proto`, install scripts fill `http://domain` and agents fail after a redirect.

The platform **does not trust** a client-forged `X-Forwarded-Host`. The public URL prefers `public_app_base`, then the request `Host`.

The bundled frontend Nginx already: listens on 80 in the container, prefers the outer `https` and will not overwrite it with the container `$scheme`. AI chat is SSE: keep `proxy_buffering` off and read timeout at least 300 seconds. Plugin / artifact uploads max about 400 MB (`client_max_body_size`).

### 11.3 CORS

Under Compose the browser talks to 8000 same-origin, so CORS is usually unused. If frontend and API are split across origins, set `CORS_ORIGINS` (comma-separated, no `*`) and fill `public_app_base`. Changing `CORS_ORIGINS` requires a backend restart.

## 12. Change domain or IP

Frontend calls are relative `/api/v1`, so they follow the address bar. In-app links in notifications are relative too.

**Already installed agents do not update themselves.** The platform URL is baked into the launcher:

| OS | Where |
|----|--------|
| Windows builder | `--server` in `start-agent.cmd` under the install dir |
| Windows node | `--server` in `start-node.cmd` |
| Linux builder / node | Address in systemd or the start script |

Correct approach: open the platform at the **new** URL, copy the install command again, and **re-run** it on every machine. The script overwrites the launcher and restarts. A same-named machine updates the existing record; id, grants, and history stay. It does not become a second machine.

Enrollment files are keyed by “platform URL + machine name”. A URL change cannot find the old file, so registration falls back to the enroll token. The command on the page already includes it.

Keep old and new URLs working during the cutover, then stop the old one. Stagger nodes so an in-flight release does not restart the agent mid-write.

Check that the script filled the new URL:

```bash
curl -s "https://new-domain/api/v1/agents/install-script?role=builder" | grep -E "Server|RELEASE_SERVER|platform"
```

If it is still `http://`, check that the outer proxy sends `X-Forwarded-Proto` and that Settings `public_app_base` is already https.

Then confirm Agents / Nodes are online.

## 13. Backup and restore

You must back up these:

1. **MySQL** (volume `mysql-data`, or `mysqldump`)
2. **backend-data volume** (secrets file, artifacts, plugins, JDK pack, branding images)
3. **JWT / AES in force at that time** (`data/.secrets.json` on the volume, or the values you put in `.env`)
4. **es-data volume** (build / AI history). Losing it only drops old logs, not pipeline definitions.

If you use Redis cron, you can also back up `redis-data`. Losing it only drops unfired cron, not pipeline definitions.

Example (from `deploy-platform/`; volume names may have a project prefix, check `docker volume ls`):

```bash
# Dump the database (needs access to the mysql container)
docker compose exec mysql mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" deploy_platform > backup-db.sql

# Volume backup: stop the service then copy, or docker run --volumes-from
docker compose stop backend
# tar backend-data and store it somewhere safe
docker compose start backend
```

Restore: start Compose, put `.env` / `.secrets.json` back to **exactly the backup-time set**, then import SQL and `backend-data`. Restoring the database without AES means every Git credential on the page fails to decrypt; you would have to re-enter them.

`docker compose down -v` deletes volumes and destroys the install.

## 14. Upgrade

```bash
cd PekaFlowAI
bash deploy/pekaflow.sh upgrade
```

Do not add `docker compose down -v`. After the image updates, volumes, secrets, and the database remain. If you already pulled, use `bash deploy/pekaflow.sh upgrade --skip-git`.

**If you changed `agent-java/src`, rebuild the jar before rebuilding the backend image**, or the platform keeps shipping the old jar and source / package names / env vars will not match. Backend start compares `deploy-agent.jar.srcsha` with current Java sources and logs a loud warning on mismatch.

```bash
cd deploy-platform/backend/agent-java
# Windows (needs JDK 8 javac)
build.bat
```

## 16. FAQ

1. **`python3` prints nothing / exit code 49 (Windows)**  
   That is the Store redirector. Use `py` or `python.exe` inside the venv.

2. **Backend log: Access denied for user 'root'@'some-ip' (1045)**  
   This is a wrong password or user@host, not a VLAN problem (that would be timeout / connection refused). The IP in `'root'@'20.10.6.4'` is the **backend's source address**. `DATABASE_URL` host must be `mysql`, not the server LAN IP. The URL password must match `MYSQL_ROOT_PASSWORD`. If you already started with a different password, the volume still has the old one: on an empty install `docker compose down -v` then start again (this wipes the database).

3. **UI opens, API 401 / CORS**  
   Under Compose use 8000; do not point Vite 5173 at a production backend. When origins are split, set `CORS_ORIGINS` + `public_app_base`.

4. **Admin cannot sign in**  
   Use `BOOTSTRAP_ADMIN_PASSWORD` if you set it. The demo password exists only on an empty database when that variable is unset. If JWT was rotated, everyone must sign in again.

5. **Assistant spins with no text**  
   No model, or the proxy buffers SSE / times out too soon. Check Models connectivity, Nginx `proxy_buffering off`, and `proxy_read_timeout` ≥ 300s.

6. **Cron does not fire**  
   Redis is down or the password is wrong. The trial Redis password is `rp-redis`. Check Redis on the health page.

7. **Execution history has no logs**  
   ES is still cold-starting, or Settings has the wrong URL. Compose defaults to `http://elasticsearch:9200`. The live phase uses Redis Stream; archive requires ES. Health will say ES down. On Linux check `vm.max_map_count`.

8. **Builder / node stays offline**  
   The machine must reach the `--server` URL (do not use `localhost` when the agent runs in a container — that is the agent itself). Check enroll token, firewall, and whether the script still says `http://` while the site is https. Windows: scheduled task running. Linux node: `systemctl status rp-node`.

9. **Install script URL is http, site is https**  
   Outer proxy did not send `X-Forwarded-Proto`, or `public_app_base` was not updated. See sections 11 and 12.

10. **Linux node JDK download 404**  
    The section 9 tar.gz was not uploaded.

11. **Jar fingerprint mismatch / start warning that jar and sources differ**  
    Java was changed without `build.bat` / `build.sh`. Rebuild, then rebuild the backend image.

12. **VM cannot reach the local backend**  
    uvicorn needs `--host 0.0.0.0`. `netstat` / `ss` should show `0.0.0.0:8080`, not `127.0.0.1:8080`.

13. **SQLite lock**  
    Occasional in development; ignore. Full trial and production use Compose MySQL.

14. **bcrypt / `__about__`**  
    This project uses native `bcrypt`. Do not install a second passlib stack over it.

15. **Frontend build: `Cannot find module 'node:path'`**  
    `npm install -D @types/node` then build again. The Compose frontend image already has the dependency.

16. **npm is slow or fails when building the frontend image overseas**  
    Frontend Dockerfile defaults to `registry.npmmirror.com`. Switch to `https://registry.npmjs.org` and `--build` again. Backend image defaults to Aliyun PyPI; same idea.

17. **Empty release manifest errors and will not pack**  
    By design: no explicit file list means refuse, never a full pack. Put the list in the step or fill it for this run.

18. **Every third-party agent tool fails**  
    harness-runner is down, or its token is not the same as the backend’s. Check `deploy-harness-runner` in `docker compose ps`. Local development without Compose refuses those tools fail-closed; they do not run inside the backend process.
