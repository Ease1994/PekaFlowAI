## 0. 一句话速览

**PekaFlowAI 是一个以 AI Agent 为交互核心的多形态发布部署平台。**

人通过自然语言驱动查询、申请权限、发起发布、诊断失败、编写插件；流水线编排与构建机/节点执行，是 Agent 落到生产环境上的手和脚。编排采用 Stage→Job→Step。**助手运行时按 DeepSeek AI-Harness（deepseek-harness / dsh）的架构思路设计**：微内核 + 插件、事件溯源 Session（日志为真源，LLM 历史是投影 Surface）、Agent Loop（turn/step）、System Prompt 分段组装、Tools 守卫执行管线、Context Compaction、Agent Skills、MCP 作为 Tool 注册源、LLM Adapter Seam、Sandbox。不是把 dsh 进程嵌进来，而是把同一套运行时概念落到发布域（FastAPI 模块 + harness-runner）。

权限、登录、通知、审计、模型与用户管理已按生产使用方式落地：**流水线执行权只能通过 AI 助手申请**；管理员在「权限管理 / 用户管理」审核与维护账号；LDAP 可用邮箱、UPN 或短账号登录；操作审计永远记真实操作人。

## 1. 项目定位与背景

- **解决什么问题**：让研发、测试、运维通过同一个入口，把应用发布到 K8s/Docker、虚拟机、Windows IIS、Tomcat、Jar 等异构环境。生产级能力包括 git 秒级拉取、步骤报错即时终止、workspace 隔离。
- **交互怎么变**：页面还在，但主路径已经是 AI Agent。查流水线、发一次版、申请执行权、看失败原因、起草插件，都应该能在对话框里完成；页面负责编排画布、审批、盯日志这些需要精细控件的事。
- **技术路线**：发布编排采用 Stage→Job→Step。**AI 以 Agent 为产品形态，运行时对齐 DeepSeek AI-Harness**：`session`（append-only `SessionEvent`，`deriveMessages` 投影）、`agent-loop`（turn = 若干 step；step = 一次模型请求 + 它唤起的 tools）、`system-prompt`（identity / persona / tool-guidance / 动态 context）、`tools`（`pre-execute` → guards → `execute` → `post-execute` → `result`）、`compaction`（tool-result-pruner + 超窗压缩）、`llm`（`Message` / `ContentBlock` / `StreamChunk` + Adapter）、Skills（调用时 `inject`）、MCP（发现工具后注册进同一 Tool 目录）、Sandbox。发布域在此之上补 RBAC 继承、确认卡片（approval / Human-in-the-Loop）、审计闭环。

## 2. 技术架构（以 AI 为核心）

平台分三层：**交互层（AI Agent）**、**编排与治理层**、**执行层（Java Agent）**。AI 不是挂在流水线上的聊天框，而是按 AI-Harness 跑起来的 Agent：权限等于当前用户，模型只通过 Tool 办事，变更走 `tools/pre-execute` 的确认/拒绝，真正动手的是构建机 / 部署节点。

### 对齐 AI-Harness 的运行时（实现对照）

产品形态是 **AI Agent**。运行时按 [DeepSeek AI-Harness](https://github.com/deepseek-ai/deepseek-harness) 的核心包来拆，而不是按「对话式 DevOps 产品」来抄。dsh 的主张：Session 日志是唯一真源；Agent Loop 可替换；能力都是 seam（Service Definition / Provider / Consumer）；扩展走事件 waterfall，不改 loop。

| AI-Harness 子系统 | dsh 概念 | 本平台模块 |
|-------------------|----------|------------|
| **Microkernel** | Cordis：plugin 贡献 service、typed event、可撤销 effect | `harness/kernel.py`：`HarnessKernel` = `ServiceRegistry` + `EventBus`（waterfall）+ `PolicyRegistry` |
| **session** | append-only `SessionEvent`；LLM 历史是 **Surface 投影**，不是另存一份 messages | `ai/sessions.py`：`AiSessionEvent` + `head_digest` 哈希链；surface：`transcript` / `model_context` / `audit` / `stream`；fork / replay / resume |
| **agent-loop** | turn 含若干 step；step = 一次模型请求 + 它唤起的 tools | `ai/chat.py`：`turn/start` → 最多 8 个 step（`complete` + `tool_calls`）→ `turn/end` |
| **system-prompt** | 分段组装，tool schema 走 tools 参数不进 prompt 正文 | `ai/prompt.py`：identity / persona / tool-guidance / working memory |
| **tools** | 守卫管线：`tools/pre-execute` → guards → `execute` → `post-execute` → `tools/result` | `harness/tools.py`：内置 in-process + 第三方 container；事件类型含 `tool/pre-execute` / `tool/approval` / `tool/result` / `tool/post-execute` |
| **llm seam** | `Message` / `ContentBlock` / `StreamChunk` + 可替换 adapter | `llm/client.py`：text / reasoning / tool_use / image 分块；`openai-compatible` adapter |
| **compaction** | 可选能力：pressure / context-overflow；tool-result-pruner 与 summary checkpoint | `ai/budget.py`：两段式 — Tool-Result Pruning（head/tail + stub）+ `fit_messages`；超窗 `CONTEXT_LENGTH` 减半重试 |
| **Skills** | 指令包，调用时 `inject()` 进上下文，不是可执行 Tool | `harness/skills.py`：`SKILL.md` + `always` / `user` / `model` |
| **MCP** | 一插件一 server：discover → `ctx.tools.register()` | `ai/mcp_server.py`：`tools/list` + `tools/call`；对内仍进同一 Tool 目录 |
| **sandbox** | 不信任代码进 isolate realm | `harness-runner`：只读容器、JSON-RPC、fail-closed；Broker 发 Capability Token |
| **approval** | `tools/pre-execute` 可 ask，人确认后再 execute | `propose_*` 确认卡片 + `POST /ai/act` 一次性签名 token |

dsh 标准 turn 流（本平台按同一顺序落地）：

```
turn/start
  assemble prompt sections + tool schemas
  step/start
  append user/message
  derive history from the log  →  compact if needed
  llm complete / stream        →  assistant/message | assistant/chunk
  tool/call → tools/pre-execute → execute → tools/post-execute → tool/result
  step/end  （tools 还欠一次请求则下一 step）
turn/end
```

┌───────────────────────────────────────────▼──────────────────────────────────┐

### 2.1 关键设计原则

1. **AI 继承当前用户，不另开特权通道。** 助手调 `propose_release` 和人在页面点执行走同一套 `check_permission`。审计里 `username` 永远是操作人，`source=ai` 只标明入口。
2. **变更必须确认。** 发布 / 回滚 / 取消 / 审批 / 节点推送生成一次性签名卡片，点确认才真正执行。申请执行权是唯一例外：提交审核单不等于立刻授权，技能直接落单。
3. **API-first。** 前端不做任何可信判断。执行权申请接口若 `source != ai` 直接 400，网页/直调 API 提交不了。
4. **Agent 拉模式。** 机器主动问平台要任务，平台不往内网推，不必给平台开放入站。
5. **扩展分四层，互不混用**（见 2.5）。助手工具、流水线步骤、第三方隔离执行是三套包格式。

### 2.2 一次对话怎么跑完

入口：`POST /api/v1/ai/chat` 或 `POST /api/v1/ai/chat/stream`。实现在 `backend/app/modules/ai/chat.py`。

```
用户消息 + 可选图片 + 所选 model_id
        │
        ▼
  写入 AiSession 事件（turn/start, user/message）
        │
        ▼
  组装 system prompt（身份 / 人设 / 工具用法 / 工作记忆）
  + 从会话投影重建历史 messages
        │
        ▼
  compact_messages() 压进当前模型的 input_budget
        │
        ├─ 有可用模型 ──► 最多 8 轮：
        │                   complete(messages, tools)
        │                   ├─ 有 tool_calls → harness_tools.dispatch()
        │                   │                 → 结果 prune 后回灌
        │                   └─ 无 tool_calls → 最终 reply
        │                 变更类技能返回 confirm 卡片（actions）
        │
        └─ 无模型 / 构建客户端失败 ──► 规则引擎（关键词 + 分级流水线匹配）
        │
        ▼
  SSE：status / reasoning / tool 进度；最后 done 带完整 reply + actions
  落库：assistant/message + 审计事件
```

要点：

- **对齐 AI-Harness：模型可见即已入日志。** 每次请求从 Session 投影重建 history，禁止另存一份「聊天表」当真源。
- **SSE 推的是 agent/session 进度，不是必须 token 流。** 当前 LLM 走 `complete()`；前端用 `done.reply` 渲染。
- **Reasoning / Content 分块。** `ContentBlock.kind` 区分；思考不进下一轮 deriveMessages。
- **Tool schema 走 `tools` 参数**（dsh 的 system-prompt 纪律），不把整份目录抄进 prompt。
- **compaction 是能力 seam**：先 pruner 再 fit；`CONTEXT_LENGTH` 走 context-overflow 策略减半预算重试。
- 无可用模型时降级规则引擎，不阻塞查目录/申请等路径。

### 2.3 模型层（`app/modules/llm`）

管理员在「模型管理」配厂商、Key、模型、看图能力；对话框左下角只列出**启用且凭证齐全（ready）**的条目，普通用户接口 `GET /ai/models` 不返回任何密钥。

| 概念 | 表 / 代码 | 作用 |
|------|-----------|------|
| 厂商 | `llm_provider` | API 地址、凭证引用、启停 |
| 模型 | `llm_model` | `model_id`、max_tokens、context_window、`capabilities`、默认模型 |
| 适配器 | `llm_adapter` | 协议。当前真正能跑的是 `openai-compatible`；DeepSeek / Anthropic / Bedrock 名字留着 |
| 任务路由 | `llm_task_route` | `assistant` / `diagnose` / `authoring` / `summary` 的主模型 + 回退；**对话主路径目前直接 `build_client(model_pk)`，诊断等走 `invoke_task`** |
| 观测 | `llm_observation` | 每次尝试的成功/失败、延迟、token |

会话级选择存在 `AiSession.model_pk`。请求带 `model_id` 会校验必须在可用清单里再写入；会话里存着的旧 id 后来被停掉，则静默回落到默认，避免整轮打挂。

**看图（多模态）**：`capabilities` 空串按模型名猜测（`gpt-4o`、`claude-4`、`vl` 等）；写成 `["vision"]` 或 `[]` 是人工标定。选中支持看图的模型后，对话框可粘贴/拖入图片（data URL，最多 8 张）随消息发给模型；不支持时按纯文字处理，未发出的预览图改成待下发附件。

`build_client(db, model_pk)` 是助手真正调模型的入口：解析厂商 + 解密凭证 + 组装 `LlmInvokeConfig`（含 context_window，供预算计算）。

### 2.4 会话与上下文

**真源是 Session 事件日志，不是聊天表**（AI-Harness `ctx.sessions`）。

- `AiSession` + `AiSessionEvent`：append-only；`head_seq` / `head_digest` 链式哈希。
- Surface 分层：`transcript`（给人看）与 `model_context`（给模型看）分开，对应 dsh「人读 append-origin、模型读 surface」。
- `project_events()` / `load_session_llm_history()` 即 `deriveMessages()`。
- fork / replay / resume / inspect / search 都从同一条日志派生。
- 旧表 `ai_conversation` / `ai_message` 仍双写兼容；新建会话绑 `legacy_conversation_id`。

**Compaction seam**（`ai/budget.py`，对齐 dsh `dsh-compaction` + `tool-result-pruner`）：

1. 过期 tool 结果先打成摘要（`stub_tool_content`），只留最近一组全文。
2. system 与最后一条 user **钉住**，从近到远按 token 预算丢掉整组历史。
3. 单条过大的 tool 结果先砍 list，再保留头尾。
4. 图片按定额计入（约 800 token/张），禁止按 base64 长度估——否则带图的用户消息会被当成超预算扔掉。

流水线识别用分级匹配（`ai/context.py`）：整名连续命中 > 业务别名 > 单个词。用户说 `test-C` 时，`order-service-test` 不能靠一个 `test` 抢走。同档多条时让用户报 id，不替他猜。

### 2.5 四层扩展：不要混

| 层 | 包长什么样 | 在哪执行 | 进助手 tools 吗 |
|----|------------|----------|-----------------|
| **内置 Tool** | `ai/skills/*.py` → `ctx.tools.register` | API 进程内 | 是，始终可用 |
| **Agent Skills** | zip：`manifest.yaml` + `SKILL.md` | 不执行，调用时 inject | 否；按 `always` / `user` / `model` |
| **第三方 Tool** | 已签名 zip + `tool.py` | **sandbox** harness-runner | 是，需启用且验签 |
| **流水线插件** | `task.json` + 入口脚本 | Java Agent（执行层，不是 agent-loop） | 否 |

内置技能按 category：

| 类 | 代表工具 | 干什么 |
|----|----------|--------|
| `catalog` | `list_pipelines` / `get_pipeline` | 查项目、分组、流水线。列表只调一次，禁止对每条再 `get_pipeline` |
| `observe` | `get_release_status` / `diagnose_release` / `list_agents` / `get_dora_metrics` | 状态、失败、诊断、构建机、DORA |
| `delivery` | `propose_release` / `propose_rollback` / `propose_node_push` | 发布、回滚、**往节点传文件**（确认卡片；落盘走内置流水线，不是技能直接写盘） |
| `access` | `apply_pipeline_execute` / `propose_review_access` | 申请与审核执行权 |
| `authoring` | `propose_plugin_draft` / `lint_plugin_source` | 插件草稿 |

研发商店（侧栏「技能库」）可下载三份详细模板：`GET /harness/templates/agent-skill`、`GET /harness/templates/agent-tool`、`GET /store/plugins/template`。工具包模板自带与平台一致的 `sign.py`。

### 2.6 第三方工具隔离（harness-runner）

第三方 Agent Tool **禁止**在 API 进程里跑。compose 里单独一个容器：

- 只挂 `harness-internal` 内网，不对宿主机暴露端口
- 非 root、只读根文件系统、`cap_drop: ALL`、内存 256m、pids 64
- 后端 `harness/runner.py` 调它；Runner 挂了是 **fail-closed**，不会退化成本地 subprocess
- 工具若要访问平台能力，经 `HARNESS_BROKER_URL` 回调 `/api/v1/harness/broker` 拿短期 token

### 2.7 MCP：注册进 Tool 目录，不取代 Agent Loop

AI-Harness 里 MCP 是「一插件一 server：discover → `ctx.tools.register()`」。本平台同样：内部调度是 agent-loop + Function Calling；`POST /mcp/tools/list`、`POST /mcp/tools/call` 把同一套 Tool 暴露给外部 MCP Host。鉴权上 `/api/v1/ai` 与 `/mcp` 都记 `source=ai`。

### 2.8 执行层（AI 的手）

同一只 `deploy-agent.jar`（JDK 8、无第三方依赖），两种角色：

- **builder（构建机）**：跑流水线 Step、拉插件 zip、编译打包
- **node（部署节点）**：只认发文件 / IIS 启停 / 还原备份，不执行任意脚本、不碰代码仓库

拉模式：`register` → 心跳 → `GET /agents/{id}/tasks` → 执行 → 上报日志 / complete。取消靠 `wait-cancel` 长轮询 + `destroyForcibly` 杀进程树。

## 4. 后端 20 个业务模块

AI 相关子集：`ai`、`llm`、`harness`、`access`（申请入口）、`pipeline/diagnose.py`（失败诊断）。

| 模块 | 职责 | 关键文件 |
|------|------|---------|
| `ai` | **助手核心**：对话循环、技能、会话事件、上下文、MCP 兼容 | `chat.py` / `sessions.py` / `budget.py` / `router.py` / `skills/` |
| `llm` | 厂商 / 模型 / 适配器 / 任务路由 / 观测 / `build_client` | `service.py` / `client.py` / `catalog.py` |

## 6. 核心机制详解

### 6.1 流水线编排模型

- **Stage → Job → Step** 三级结构，YAML as Code（`pipeline.yaml`）。
- 前端 React Flow 可视化，后端 `graph.py` 图形↔YAML 互转。
- 每个 Job 带 `agent` 标签（如 `linux` / `maven`），决定由哪台构建机执行。
- 环境码必须与构建机/节点一致，对不上在派任务时直接报错。

### 6.2 发布状态机

```
pending → queued → running → success / failed / cancelled
                            └→ rolling_back → rolled_back
```

- **生产分组**：创建 release 后进 `pending`（待审批）→ 审批通过进 `queued`。
- **测试分组**：免审批，直接 `queued` → 执行。
- 执行历史展示 **发布人**（`operator_name`）。同一流水线有执行权的人能看到所有人的发布记录。

### 6.3 Agent 拉模式执行（agent-java）

```
启动 → POST /agents/register（拿 agent_id + token）
     → 心跳循环 POST /agents/{id}/heartbeat（每 10s）
     → 拉任务 GET /agents/{id}/tasks（轮询，默认 2s）
     → 有任务：执行 Job 步骤，逐条 POST .../log 上报
     → 完成 POST .../complete（success 布尔）
```

- **JDK 8 单 jar，无第三方依赖**，`--server --name --tags --poll --workspace`，节点再加 `--role node`。
- 鉴权：直连接口校验 `X-Agent-Token`（注册时下发）。

### 6.4 步骤失败即终止 + 取消信号

**双层防护**：

1. **后端级联**：`complete_task` 收到失败 → 同 release 下 pending/assigned/running 任务全部 `cancelled`，release 标 `failed`。
2. **Agent 主动 kill**：`POST /agents/{id}/tasks/{taskId}/wait-cancel` 长轮询（最多 60s），收到信号 → `destroyForcibly` + 杀进程树（Windows `taskkill /F /T /PID`，Linux `kill -9 -PID`）。

`POST /releases/{id}/cancel` 能真正杀进程。`fetch_task` 过滤已终止 release，不再下发。

### 6.5 git 拉取加速（bare mirror 缓存）

**目标**：对标蓝鲸「git 秒级拉取」。

- 检出：`git clone --depth 1 --single-branch --no-tags -b <branch>`。
- 本地镜像：`~/.release-agent/git-cache/<sha1(repoUrl)>.git`（bare，全历史）。首次建缓存慢一次；之后 `git fetch --prune` 秒级增量，`git clone --reference <cache> --dissociate` 秒级落到 workspace。
- **铁律**：`--reference` 仓库不能是浅克隆。更新前 / fetch 后检查 `shallow` 与 `alternates`，不可用则删掉重建；reference 失败则降级普通浅克隆。

### 6.6 定时触发（Redis 延迟队列）

- Redis ZSET `cron:queue` + `croniter`。后台每 15s 扫到期项（原子 `ZREM`），每 30s 同步 cron。
- **API 不主动连 Redis**，不可用自动降级，配好后恢复。配置在「平台设置 → Redis」。

### 6.7 RBAC 与执行权申请

授权粒度到 **项目 / 分组 / 流水线**：

| 资源 | 操作 |
|------|------|
| 项目 | 查看 / 创建 / 更新 / 删除 |
| 分组 | 以上 + **审批（approve）** |
| 流水线 | 查看 / 创建 / 更新 / 删除 / **执行（execute）** |

- 继承：项目权覆盖旗下分组与流水线；分组权覆盖旗下流水线。admin 全权。
- 校验只在后端 `app/core/deps.py` 的 `check_permission`。

**执行权申请**（`access`）：

- 用户通过 AI 技能 `apply_pipeline_execute` 提交。`POST /access/applications` 若 `current_source() != "ai"` 直接拒绝。
- **申请走 AI，执行本身不限 AI**：有 execute 权限后，页面/API 都能触发发布。
- 通过后默认只写入该流水线 `read` + `execute`。管理员审批时可改拟授权限。
- 记录落 `permission_application`，不可物理删除。

### 6.8 站内审核通知

表 `in_app_notice`（MySQL，不进 ES）。申请后通知管理员及分组 `approve` 权限的人；通过/驳回后通知申请人。前端顶栏 `NoticeBell`。

### 6.9 操作审计

落 `audit_log`：

- **`username` 永远是当前操作人**，不是「AI」。
- **`source`**：`web` / `ai` / `api` / `cron`。`/api/v1/ai` 与 `/mcp` 记 `ai`。
- AI 发起时 detail 里带 `skill=`。

### 6.10 用户管理

独立模块 `account/`，页面 `/users`（仅管理员）：新增/编辑/重置密码/启用禁用/删除、LDAP 搜索导入、测连通。`user.source` 为 `local` / `ldap` / `wecom`。禁用账号无法登录。

### 6.11 LDAP / 本地 / 企业微信登录

**本地**：短账号 + 本地密码（空库只有 `admin`）。

**LDAP**（平台设置打开并填绑定）：过滤器兜底 `mail` / `userPrincipalName` / `sAMAccountName`。含 `@` 且未启用 LDAP 时明确提示，不会误当成不存在的本地用户。`ldap_auto_provision` 控制首次域登录是否自动建档。

**企业微信**：OAuth2，`wecom_auto_provision` 控制自动建档。

**API Token**：sha256 存储，权限与用户相同。

### 6.12 构建日志存储

固定 **Redis Stream 实时缓冲 + Elasticsearch 按日归档**。Compose 默认带本栈 ES；设置页可改地址和构建日志索引前缀（实际索引 `{前缀}-YYYY-MM-DD`）。AI 审计走 `rp-assist-logs-YYYY-MM-DD`。

硬隔离：

- 历史日志只在 ES。Redis 只给正在跑的任务做实时尾巴；**写入 ES 成功后立刻从 Redis 删除**，key 最多留 1 小时。
- 构建日志**禁止**回写 `build_task.logs` / `build_task_log` / `release.logs`，也**禁止**攒进程内存。
- 没有构建任务时的启动失败原因写在 `release.error_message`（短业务字段），不是日志。
- 业务数据只进数据库，库挂了不能把数据塞进 ES。
- ES 或 Redis 挂了：这一批丢掉、页面可能暂时看不到日志；发布、领取任务照常跑。
- `log_storage=mysql` / `redis` 配置会被忽略，一律按上面走。

### 6.13 流水线复制 / Rebuild / 代码变更

- **复制**：`POST /pipelines/{id}/duplicate`，名字加 `_copy`。
- **Rebuild**：用原 release 的 `source_ref` 重建，保证拉的是发布那次的代码。
- **代码变更**：`GET /releases/{id}/commits` 调 GitLab/GitHub API 返回两次发布之间的 commit 区间。

### 6.14 启动补丁（已有库升级）

`create_all` 不会 ALTER 已有表。`main.py` 的 `_ensure_schema_patches()` 启动时按需补列/补表（含 `ai_session.model_pk`、`llm_model.capabilities` 等），**不清空业务数据**。LLM 表还有 `ensure_llm_schema()`。

## 11. 关键约定与踩坑记录（务必阅读）

| # | 坑 | 说明 / 正确做法 |
|---|----|----------------|
| 1 | **`python3` 是坏的** | 本机 `python3` 指向 Windows Store 重定向器，一律用 `py` 或 `.venv/Scripts/python.exe` |
| 2 | **`metadata` 是 SQLAlchemy 保留名** | Artifact 表该字段属性命名为 `extra_meta` |
| 3 | **固定路由要在动态路由之前** | 如 `/releases/statistics` 必须在 `/releases/{id}` 之前 |
| 4 | **统一响应** | `R.ok()` 内部已做 ORM→dict 序列化 |
| 5 | **删库不能用 `rm`** | 重置数据用 `Base.metadata.drop_all` |
| 6 | **JDK 8 无 `Process.pid()`** | pid 用反射 `ProcessImpl.pid`；杀进程树 Win `taskkill /F /T /PID`、Linux `kill -9 -PID` |
| 7 | **`--reference` 不能指浅克隆** | 缓存坏了先删 `~/.release-agent/git-cache/<hash>.git` |
| 8 | **`--reload` 会被长轮询卡死** | `wait-cancel` 占着请求；生产用无 reload + 手动重启 |
| 9 | **workspace 必须 `p-{uuid}`** | 不要按 pipeline/repo 复用，并发会互踩；秒级拉取靠 bare mirror |
| 10 | **Agent 旧 token 循环 401** | 重启后旧进程还挂着会 401，需 `pkill -f "java.*deploy-agent"` |
| 11 | **bat 中文编码** | Git Bash 直接跑 build.bat 会乱码，用 cmd 或手动 `javac`+`jar` |
| 12 | **LDAP 用邮箱登不上** | 先确认平台设置已启用 LDAP 且绑定密码已填 |
| 13 | **权限申请接口 400** | 网页/直调 API 不能提交，必须走 AI 助手（source=`ai`） |
| 14 | **测试机 docker-compose** | 现场常用带横杠的 `docker-compose` |
| 15 | **harness-runner 缺 token 起不来** | compose 要求 `.env` 中 `HARNESS_RUNNER_TOKEN` |
| 16 | **不要给 harness-runner 写 `cpus`** | 部分机器 cgroup 不支持 `cpu.max`，容器会起不来 |
| 17 | **流水线名不能靠单词子串匹配** | `test-C` 不得命中 `order-service-test`；改匹配算法时先跑 `tests/test_pipeline_matching.py` |
| 18 | **思考内容禁止回灌** | 把 `reasoning_content` 拼进下一轮 messages 会把窗口吃光后突然断开 |

1. **先跑通 AI 主路径**：起后端 + 前端，在「模型管理」配一个可用模型，打开 AI Agent，列出流水线，对一条测试流水线说「发布一下」，核对确认卡片上的 **id + 名称** 没认错。再走一遍：AI 申请执行权 → 管理员审批 → 顶栏铃铛。
2. **再跑通执行路径**：起一个 Agent，跑一条流水线，看执行详情日志、取消、第二次 git 秒级效果。
3. **改后端代码后**：不用 `--reload` 时必须杀掉 uvicorn 再启动；Docker 则 `docker compose build --no-cache backend frontend harness-runner && docker compose up -d`。
4. **改 Agent 代码后**：重新打包 jar → 替换 → 重启各构建机/节点。
5. **数据库升级**：不要删库。重启后端会跑 schema 补丁。
6. 功能按模块说明见 `deploy-platform/docs/发布部署平台-功能说明书.docx`（可用 Word 打开）。更多实现细节见 `deploy-platform/README.md`、`deploy-platform/docs/部署文档.md`、`deploy-platform/docs/功能说明书.md`、`backend/agent-java/README.md`。需要重生成 Word 时，在 `deploy-platform/docs/` 下执行 `python gen_func_docx.py`。
